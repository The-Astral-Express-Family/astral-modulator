# 仓库卫生自检（repo hygiene）

目标不是"代码能跑"，而是**下一个任务的实现者不会因为上一个任务变得更慢**。

本 skill 自包含：不在目标仓库安装任何脚本；唯一的落盘物是仓库根两个可选
配置文件（见 §0），缺失时用内置默认值也能跑。分两档运行：

| 档位 | 时机 | 内容 |
|---|---|---|
| 快速档 | 每完成 3–4 个任务 / 单次大改动后 | A（机械检查）+ B 的 1–4 条 + 本次新增文件的过目 |
| 完整档 | 每个里程碑/阶段/PR 批次收尾 | A + B + C + D 全部，且必须派发 subagent 独立复核 |

## 0. 首次在某仓库运行（一次性校准）

1. **测试命令**：找到本仓库的权威测试/typecheck/build 命令（package.json
   scripts、Makefile、pyproject.toml、Cargo.toml、CI 配置……），
   后续 §A 直接用它们，不要假设某个包管理器。
2. **阈值**：跑一遍 §A 的脚本看文件行数分布（脚本会打印最大的 10 个文件），
   按分布定 warn/fail，写入仓库根 `.hygiene.config.json`（提交进库）：

   ```json
   {
     "limits": {
       "source": { "warn": 600, "fail": 900 },
       "test":   { "warn": 1000, "fail": 1500 },
       "doc":    { "warn": 600, "fail": 900 }
     },
     "allowlist": {},
     "ignore": []
   }
   ```

3. **标记基线**：第一道完整档通过后加 `--update-baseline` 生成
   `.hygiene-baseline.json`（提交进库），之后每道门对比 TODO/FIXME/HACK
   总数不得上升。

阈值与豁免属于仓库资产，校准后落盘；这是本 skill 在目标仓库的唯一状态。

## A. 机械检查（先跑，零判断）

```bash
node <本 skill 目录>/scripts/hygiene-check.mjs    # 行数阈值 + 临时标记扫描，超限即 fail
<本仓库的测试命令>                                # 红 = 一切暂停
```

（`<本 skill 目录>` = 本 SKILL.md 所在目录，skill 加载时会给出其绝对路径。）

- 脚本用 `git ls-files` 取文件清单（含未忽略的新文件），按文件名模式与
  扩展名自动分类源码/测试/文档，不依赖仓库里预置的任何脚本；环境没有
  node 时用等价 shell 代替：
  `git ls-files '*.ts' | xargs wc -l | sort -n | tail` +
  `grep -rw -e TODO -e FIXME -e HACK . --include='*.ts' -c | awk -F: '{s+=$NF} END {print s}'`。
- 超限的**既有豁免**登记在 `.hygiene.config.json` 的 `allowlist`
  （键 = 路径或目录前缀，值 = 原因 + 清偿任务号）；新文件一律不得进豁免清单。
- 源码里的 `TODO`/`FIXME`/`HACK` 数量不得比上一道门增加（脚本对比基线
  输出，人工核对）。

## B. 结构检查（读代码，subagent 复核）

完整档必须把下面这段 prompt 原样派发给一个**只读** subagent（general-purpose
或 Explore），不要自己检查自己：

> 你是代码评审员，只读不改。仓库根：本仓库。范围：`<git diff --name-only <上一道门的基线提交/标签>..HEAD>`
> 加上这些文件：`<本次新增/重点文件列表>`。逐文件检查以下七条，输出问题清单，
> 每条格式 `文件:行号 [严重度 P1|P2|P3] 一句话问题 + 一句话修复建议`。没有问题的条目
> 不要编造。不要修改任何文件。
> 1. 单函数体 > 80 有效行 → 拆分为可命名的小函数；
> 2. 分支/循环/try/回调嵌套 > 4 层 → 早返回、抽函数、或数据结构化；
> 3. 相似代码块出现 ≥ 3 处 → 抽公共函数/类型；仅 2 处且语境不同 → 容忍；
> 4. 冗余逻辑：对同一数据重复校验/重复派生；对 schema 校验器（zod / pydantic /
>    JSON Schema 等）已校验的输入再手写一遍校验；
> 5. 过度防御：对内部调用方校验"不可能发生"的状态并静默兜底（吞错 catch、
>    undefined 兜底掩盖 bug）——内部不变量用断言/类型表达，跨边界才校验；
> 6. 补丁叠加：为绕开旧调用点而新增带默认值的参数、同名函数第二实现、
>    注释里出现"兼容/暂时/legacy/旧路径"——应重构旧路径而非并排新路径；
> 7. 死代码：未被引用的导出、被替换系统残留、永不进入的分支。

收到清单后：P1/P2 **当场修复**（这是门的一部分，不是后续工作）；P3 记入
仓库的偏差/待办记录（没有就记入本次会话小结）。修复后重跑 A。

## C. 契约与单一真源（每道完整档必查）

1. **单一真源**：每类数据只有一个权威存放处。用本仓库的领域概念逐一
   枚举（状态、事件流水、缓存、派生数据、配置各问一句"权威在哪"），
   发现第二存放处即 P1。
2. **冻结契约**：改冻结 schema/协议/API 的字段集 = 停下登记阻塞，不允许
   顺手改（版本号递增 + 偏差记录是唯一合法路径）。
3. **依赖方向**：核对仓库自己声明的分层规则（architecture test、import
   lint、README 架构图……）；新增目录必须纳入其扫描范围；仓库没有等价
   机制时，用 grep 抽查核心层是否 import 边界层。
4. **配置**：删除的系统能力对应的配置键一并删（config 无死键）；新增
   配置键必须有默认值且被读取。

## D. 文档卫生（每道完整档必查）

1. 进度文档（状态页 / 清单勾选）与实际行为一致——以测试为准，不以记忆为准；
2. 本阶段设计偏离已记入仓库的决策/偏差记录；重大偏离已回写设计文档；
3. 源码注释中的文档/章节引用仍可解析（被引文件与章节还在；仓库没有
   此约定则跳过）；
4. 新文档进仓库的文档索引/地图（若有）；超过阈值的文档拆分或归档
   （历史文档移入归档并注明）。

## E. 修复纪律（怎么处理发现的问题）

- **发现即修**：卫生问题不排"后续批次"，门的含义就是此刻通过；
- **重构优先于叠加**：改不动旧代码时，先重构使改动容易，再落新逻辑
  （"先移动再修改"两步分别 commit）；
- **测试随缝拆分**：源文件沿某条缝拆了，对应测试文件沿同缝拆，禁止留一个
  巨型测试文件配多个小源文件；
- **一次只修一类**：混在功能 commit 里的卫生重构单独成 commit
  （`refactor(scope): …`），保持 blame 可读。
